01 / THE GUIDE

Understand the package

OCI gives files a common way to be packaged, identified, and delivered.

OCI means Open Container Initiative. Its standards grew out of software containers. The packaging and distribution specifications also support ordinary data: models, point clouds, images, invoices, or reports. Publishing these files does not require running them as containers.

The Image specification defines package structure; the Distribution specification defines transfer. The separate Runtime specification concerns executing containers.

ORAS is a client that publishes and retrieves OCI artifacts. OCI is the standard; ORAS is one implementation. A compatible registry is the service at the other end.

About the Open Container Initiative · OCI guidance for non-container artifacts · ORAS clients and registries

Digest = exact content. A fingerprint calculated from bytes. Change a file and its digest changes; the manifest referencing it changes too.

Tag = convenient label. A name such as “current” can point to a different version later. Record digests when a result must be reproducible.

OCI image manifest 1.1.1 · OCI descriptors and content fingerprints · OCI distribution 1.1.1

A new version references the new report and the unchanged record and photograph. The “current” tag can move; retained Version 1 is still addressable by its digest.

OCI identifies versions; your service decides what to retain. It does not automatically split large files, merge edits, or approve a release.

Technical detail: addresses, types, and linked results

A repository groups artifacts inside a registry. A tag reference looks like registry.example.org/team/inspections:current; an exact reference uses @sha256:… instead of the tag. These are registry references, not browser download links.

A media type identifies an encoding, such as image/jpeg. An artifact type describes the package kind. A subject points from a result artifact to another artifact; referrer discovery finds those attached results. Multiple inputs need an agreed provenance record listing every exact input.

A digest checks bytes, not authorship or correctness. An approval, trusted signature, retention rule, and access policy each do a different job.

02 / THE GUIDE

Connect the infrastructure

Separate the place information lives, the code that moves it, and the code that uses it.

The original authority

A file service, authoring tool, ERP, or site application owns the live information. Read a specific version or capture a consistent snapshot. Keep the source link and permissions. Live changes and approvals continue through its API.

Examples: Autodesk Docs, SharePoint, Business Central. A file package does not replace invoice posting or a shared editing session.

The bridge to OCI

The connector reads a supported API or accepts an export. Mapping code prepares the content. An OCI client such as ORAS uploads (pushes) or downloads (pulls) the package.

Build this handoff: source-version capture, field mappings, retries, and result return. A manual export can be enough for a first workflow.

The package service

A registry exposes the OCI distribution API. It stores manifests and blobs, often using disk or object storage underneath. Applications use the registry API; an ordinary storage bucket alone is not a registry.

A managed option such as Azure Container Registry or an independently operated Harbor installation can fill this role. Test your artifact types, permissions, referrers, retention, and restore.

The useful operation

A viewer, script, licensed engine, or agent reads a supported package and produces a result. Long jobs can use a queue and worker. Publish the output with its input versions and processing history.

Run this code separately from the registry: on a workstation, VM, container, or suitable hosted service. OCI storage does not execute it; Kubernetes is optional.

The place people work

A small interface lists available information and compatible operations. A catalog or search database indexes permitted metadata. It can be rebuilt from retained publications and source records.

Start with a configured app list. The registry does not provide business search, a universal app launcher, or compatibility between every file and every application.

The services around the workflow

Use organizational sign-in and scoped service identities. Apply access rules at sources, registry, workers, and search. Keep credentials in a secret manager; record activity, failures, and restore procedures.

Sharing a sign-in provider does not automatically copy permissions between systems. Name the service owner and keep the existing business approval route.

Follow one request through the system

“Import from” means a connector reads an authorized source version and maps it into supported content. “Open with” means the interface selects a compatible application, grants scoped access, and passes the exact package reference. These actions require application code.

03 / THE GUIDE

Give the content meaning

A client can deliver every byte correctly and still misunderstand the information.

MEANINGWhat is this thing?

Identity, units, relationships, responsibility.

REPRESENTATIONHow is it written?

A native file, open model, table, or image.

OCIWhich exact package?

A manifest, content fingerprints, and delivery.

Agree a small content profile: required files, their roles, supported encodings, units, identifiers, and source links. This is how two applications know what they can exchange. OCI and a semantic standard such as IFC can be adopted independently.

Example: why model semantics change the work

Door property

Resolve the right value

Door → type
+ instance override

A checker follows the type relationship and any override, preserving the door’s identity.

Chair placement

Reuse the shape

One chair shape
→ many placements

A move can change a placement without rewriting the shared shape, if the representation preserves both.

Wall cost

Process relevant values

Wall quantities
× agreed rates

A rate change can leave geometry reusable. Recalculating every wall may still touch every cost partition.

Object identity tracks the same door through changes; a digest tracks exact bytes. An authoring layer expresses contribution and precedence; a storage chunk is a transfer unit. Neither pair is interchangeable.

What the reported IFC5 experiment establishes

On 29 October 2026, helenkwok reported testing four Nordic BIM4LCA permit/as-built Revit pairs exported to IFCX. The author reports exact recomposition in 504 measured releases. These are reported results, not an independently reproduced benchmark.

Largest releaseDoor editFurniture moveWall-cost edit
Whole JSON38.2 MB38.2 MB38.3 MB
Parquet property families9.8 kB10.6 MB10.6 kB
Exact base + change file8.5 kB11.7 kB14.0 kB

Values are reported new bytes including the experiment’s flat JSON manifest, assuming prior content is held. The base-dependent real revision was 0.74 MB.

  • JSON was uncompressed; Parquet used zstd. The single gzip file was 2.37 MB: compression must be normalized before comparing layouts.
  • Fine partitions produced a 2.74 MB manifest; Parquet footers also burden tiny changes. Request costs and two-level manifests were unmeasured.
  • Conflicts and long-chain compaction remain unresolved; the scripted edits omit dependent authoring updates.
  • The exporter baked world-coordinate meshes without placements. Placement-only chair moves were not measured.

The gains belong to representation, partitioning, reproducible exports, and base-reusing change files. They do not establish an OCI-specific speed or cost advantage. Reported IFC5 experiment by helenkwok, 29 October 2026

IFC5 is evolving. Use supported formats for an operational pilot, and validate emerging representations separately. IFC5 development scope and limitations

04 / THE GUIDE

Apply the same pattern

Exact input → useful operation → linked result → existing review.

The examples below are proposed implementations using documented building blocks. They can start inside one organization; a partner does not need to adopt OCI.

Example · Repeatable checks

“Can we reproduce this result?”

An AEC information manager checks a weekly model delivery. A startup can use the same pattern to rerun internal calculation fixtures after an engine update.

Should an agent operate on software or data?

Give it structured data for reading, comparing, and calculating. Give it a scoped software API when it needs an authoring engine, a live transaction, or a workflow action. Use UI automation when a suitable API is unavailable. OCI supplies exact inputs and retained outputs; it supplies none of those operations.

Rapidly generated apps can reuse these contracts. They still need correctness tests, permission checks, and a maintenance owner.

05 / THE GUIDE

Try the mechanics locally

Publish an inspection, attach a review, then copy both.

This exercise uses ORAS and two local folders in OCI layout format. No cloud account or registry server is needed. It demonstrates packaging and links; authentication and enterprise workflow come later.

Run the exercise · ORAS 1.3.5 · bash or zsh

Install the pinned ORAS version and run this in a writable directory. It creates a new inspection-lab folder with synthetic data. ORAS installation

set -eu

mkdir inspection-lab
cd inspection-lab

cat > inspection.json <<'JSON'
{
  "asset_id": "door-042",
  "location": "Level 2, east stair",
  "finding": "Closer needs adjustment",
  "status": "open"
}
JSON

oras push --oci-layout source:v1 \
  --artifact-type application/vnd.example.inspection.v1 \
  inspection.json:application/json

inspection_digest="$(oras resolve --oci-layout source:v1)"

cat > review.json <<JSON
{
  "input_digest": "$inspection_digest",
  "decision": "needs-review",
  "next_action": "Assign to the site lead"
}
JSON

oras attach --oci-layout "source@$inspection_digest" \
  --artifact-type application/vnd.example.inspection-review.v1 \
  review.json:application/json

oras discover --oci-layout "source@$inspection_digest"

oras cp --from-oci-layout --to-oci-layout --recursive \
  "source@$inspection_digest" received:v1

oras pull --oci-layout "received@$inspection_digest" \
  --output received-files
oras discover --oci-layout "received@$inspection_digest"
cmp inspection.json received-files/inspection.json

Both discover calls should list the linked review. The final cmp should succeed silently. Pulling the inspection retrieves its files; the review is a separate artifact you can pull by its own digest.

The custom example types are not industry standards. Some ORAS 1.3 options, including recursive copy, are preview: pin and retest the client.

ORAS push · ORAS resolve · ORAS attach · ORAS discover · ORAS copy and referrers
Then replace the synthetic result with a real operation

For a model check, supply an agreed IFC model and IDS ruleset to a pinned IfcTester installation:

python -m ifctester requirements.ids model.ifc -r Html -o report.html

Publish the report with both input versions, tool version, and execution record. Failed requirements are findings; a crashed worker is an execution failure. Keep those outcomes distinct. IfcTester usage and reports

Next, copy a test package into a provisioned registry using its supported sign-in flow. Test a read-only identity, denied access, attached-result retention, and restore. The local exercise cannot establish these properties.

06 / THE GUIDE

Decide what is worth operating

Start with one complete workflow. Add infrastructure when a measured need justifies it.

First deployment

One source/export, one agreed profile, one compatible store, one operation, and one result in the current review process. Reuse existing identity and hosting.

Before relying on it

Name an operator and backup. Test representative good/bad inputs, source changes, denied access, retries, and restore. Budget connector, ruleset, and dependency upkeep.

Price the whole workflow: connector + mapping + interface work, domain review, licenses, hosting, storage/transfer, support, and retained versions. Compare correctness, repeated effort, review time, and cost per accepted result against today’s process.

Enterprise controls and the limits of OCI

Enforce access separately at each service; minimize worker permissions and separate proposed results from authorized writes. Isolate processing of untrusted files, validate outputs, log input/output references, and monitor failures. Container-image scanning alone does not validate arbitrary documents or models.

Test large uploads, referrer discovery, revocation, backup, restore, and export. Keep required attached results through retention and garbage collection. A content fingerprint is neither an access control nor an indefinite preservation guarantee.

OCI packaging and distribution have established infrastructure. Domain content profiles, federation records, application launch contracts, and cross-system permission mappings still need agreement and validation.

When something simpler—or a different service—fits better
NeedStart here
One task entirely inside an existing platformIts API and current review workflow. OCI may add no useful portability.
Store and retrieve files for one consumerOrdinary object storage and version metadata may be enough.
Query or update individual recordsA database or transactional API. Keep ERP posting in the ERP.
Live collaborative editingAn editing/synchronization engine with conflict handling.
Spatial queries or continuous telemetryA spatial database or streaming system; publish selected snapshots/results when useful.

Stop or simplify if inputs cannot be interpreted reliably, permissions cannot be enforced, nobody owns maintenance, or the measured benefit does not cover the burden.

Who pays, who benefits, and why participate?

Better information often costs the producer time while saving someone else work. Open standards do not resolve that mismatch. Fund bounded deliverables, acceptance tests, correction duties, and ongoing updates explicitly.
